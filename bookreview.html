C-2 VS Code installer URL bug is documented but left unfixed in the book's code Ch09
Known Bug

Chapter 9 explicitly calls out a "Known Bug" in the Phase 2 build script: the VS Code download URL uses the win32-x64 variant (user installer) instead of win32-x64-system (system installer). For a Windows 365 multi-user / VDI environment, the system installer is mandatory — it installs VS Code to Program Files, is available to all users, and does not self-update per-user. The user installer installs into AppData, which breaks Silent Install behaviour and causes extension conflicts under Active Setup.

The bug is acknowledged in a callout box and never corrected in the code listing beneath it. Any reader who copies the script will provision Cloud PCs with the wrong VS Code variant. This is a functional breakage on every image build, not a theoretical risk.

Recommendation: Fix the URL in the code listing to use win32-x64-system and remove the Known Bug callout. The callout is appropriate only if the correct URL is pending confirmation — if the correct URL is known (it is), the fix should be in the code.

M-5 Ch39 assumes managed identity auth for Key Vault — Windows 365 Cloud PCs have no system-assigned MI by default Ch39
Completeness

Chapter 39's Key Vault integration section recommends: "The Cloud PC or VM should have a managed identity assigned and granted Key Vault Secrets User on the vault; the az CLI will pick up managed identity credentials automatically." Unlike Azure VMs, Windows 365 Cloud PCs do not support system-assigned managed identities — they are not VMs the operator controls at the ARM level. A user-assigned managed identity can be attached indirectly, but the mechanism for doing so with Windows 365 Cloud PCs is non-trivial and platform-specific.

Readers who follow this guidance for their Windows 365 fleet will find that az login --identity fails because no identity is attached. The fallback is interactive az login or a service principal with client secret — neither is production-appropriate for automated scenarios. The gap between the instruction and the actual Windows 365 constraint is significant.

Recommendation: Add explicit guidance on the Windows 365-specific path to managed identity: either using a secondary user account with federated credentials, or using Azure AD-registered app credentials stored in Key Vault itself. Alternatively, recommend az login as the developer workstation path with a clear note that production fleet Key Vault auth requires a different approach on Windows 365 vs. Azure VMs.

M-8 OneDrive Known Folder Move is required for DR failover but not mentioned in first-login or Intune chapters Ch41 / Ch22 / Ch32
Completeness

Chapter 41 (Disaster Recovery) lists "OneDrive Known Folder Move enabled for all users" as a DR readiness prerequisite and explains that only OneDrive-backed files are preserved across failover. This is a critical operational dependency: if Known Folder Move is not configured, users lose anything on their Desktop, Documents, or Pictures during a regional outage. However, Chapters 22 (First Login) and Chapter 32 (Intune Configuration Profiles) — the natural locations for this configuration — do not mention it.

The result is that a reader who deploys the book without reading Chapter 41 will have a fleet without Known Folder Move configured, which they will only discover is a gap when they read the DR chapter — or worse, during an actual outage.

Recommendation: Add OneDrive Known Folder Move configuration (via Intune Settings Catalog policy) to Chapter 32 or Chapter 22, with a forward reference to Chapter 41 explaining why it matters for DR. This is a standard Windows 365 best practice that belongs in the provisioning/configuration section, not only the DR chapter.
