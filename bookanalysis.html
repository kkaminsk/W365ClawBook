Critical stubs (≤4)

The book is in strong overall shape for a practitioner audience. Parts I–IV demonstrate consistent clarity and technical depth. The highest-risk items are Chapter 32 (Intune Configuration Profiles, score 4 — a stub requiring full expansion), Chapter 34 (Troubleshooting FAQ, score 5 — bullets without actionable steps), and Chapter 24 (VS Code Extensions, score 6 — ends abruptly and contains a logical contradiction). Chapter 40 (Decentralized Identity, score 6) is technically sound but assumes Web3 literacy the target audience does not have. Ten cross-cutting issues — primarily undefined terms, terminology inconsistencies, and misplaced content — recur across multiple parts and should be resolved globally rather than chapter by chapter.

Cross-Cutting Issues (appear in 3+ chapters)
1
"Hydration" used for three distinct mechanisms Critical
The word "hydration" is used across the book to mean: (a) GitHub Desktop's per-user install trigger at first login (ch09), (b) the Active Setup script that copies config templates to a user profile (ch10, ch22), and (c) a general conceptual term for first-login state population (ch15, ch36). These are mechanically different operations and sharing a term creates silent confusion when readers try to troubleshoot or extend the pipeline. Each use should be given a distinct name — e.g. "GitHub Desktop hydration" → "per-user install activation," "config hydration" → "config template copy via Active Setup."
ch09ch10ch15ch22ch36
2
"Active Setup" used without definition across 8 chapters Critical
Active Setup (the Windows registry mechanism that runs a command once per user on first login) is introduced in ch02 and used through ch36 without ever receiving a complete definition in prose. It appears in chapter headings, checklist items, the component matrix, and runbook instructions. Readers who focus on Azure/Intune rather than Windows desktop internals will not know what path to check or what a correct value looks like. A single canonical definition — ideally in ch10 where the mechanism is first used practically — should be the global reference.
ch02ch03ch07ch10ch15ch22ch34ch36
3
"mcporter.json" never defined High
The filename "mcporter.json" appears in chapter 10 (Phase 3 config), chapter 22 (first-login walkthrough), and chapter 37 (component matrix) without any explanation of what "mcporter" is. The config directory is named "mcp" while the file is "mcporter.json," which compounds the confusion. Readers cannot determine whether mcporter is a separate tool, an OpenClaw subsystem, or simply a config filename convention. A one-sentence definition at first use in ch10 is needed.

4
"Agent account" / "dedicated agent account" / "agent identity" used interchangeably High
The canonical identity concept introduced in ch01 and architected in ch27 is called "agent account," "dedicated agent account," and "agent identity" across different chapters with no indication these are synonymous. In ch39, "agent account" is reused in a different sense (the runtime process identity rather than the Entra object). Pick one term — "agent account" is the most established — and apply it globally.

5
British vs. American English spelling inconsistency Medium
"Artefact" (British) appears in chapters 04, 18, and 21 while GitHub Actions YAML and most prose uses "artifact" (American). The word "optimisation" appears in ch36's Teams entry. The book should standardize on American English throughout, as the surrounding Microsoft and GitHub tooling ecosystem uses American spelling in its own documentation.

6
ClawHub called "marketplace" in some chapters and "registry" in others Medium
"Marketplace" and "registry" convey different architectural meanings — a marketplace is a store, a registry is a package index. Ch10 calls it "the public ClawHub marketplace," ch13 calls it "the OpenClaw ecosystem's ClawHub registry," and ch29 uses both. This is not a trivial distinction for platform engineers designing access controls. Standardize on one term and define it once.

7
ClawHavoc "12%" statistic introduced without citation High
Ch26 states "approximately 12% of skills in the ClawHub registry were malicious" as a near-fact with no citation. Ch13 repeats the figure but immediately hedges: "independent verification varies by source." This hedging undermines the threat narrative's credibility for an enterprise security audience who will scrutinize supporting data. Either cite a specific source or reframe as: "Community advisories have flagged multiple malicious skills in the ClawHub registry — this pattern, consistent with npm/PyPI supply-chain attacks, motivates the controls in this chapter."
ch13ch26ch29

Chapters opening cold with code blocks before conceptual framing Medium
Several chapters drop readers directly into a code block or table with no introductory sentence establishing context. This is fine for a reference appendix but not for chapters that appear in a linear read path. Affected chapters: ch14 opens with a terraform apply block, ch15 opens with a table with no intro, ch36 has checklist items with no lead-in prose. Each needs one or two orienting sentences before the first structured element.

Misplaced content across chapter boundaries High
Three chapters contain substantial content that belongs in a different chapter: (1) ch23 (API Key Delivery) has a full "Post-Provisioning Agent Delivery via Intune" section that belongs in ch25 (Agent Updates). (2) ch33 (Monitoring and Forensics) ends with a build troubleshooting guide relevant to Part III. ACG (Azure Compute Gallery) and AIB (Azure VM Image Builder) are defined in Parts I–II but used without expansion in Parts IV–VII. Readers who use Part IV or Part VII as standalone runbooks — which the book explicitly invites — will encounter undefined acronyms.
